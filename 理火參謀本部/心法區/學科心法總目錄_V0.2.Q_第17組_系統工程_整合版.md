## 主要方法取向與心法卡

### 需求與查證追溯

```yaml
METHOD_CARD:
  core_question: 誰在何種情境需要怎樣的服務？
  first_move: 列任務、場景、可觀測門檻及負責人。
  evidence_preference: 使用者需求、正式配置與驗收證據。
  causality_model: 漏列降級需求使採購及驗收無法覆蓋。
  actor_model: 需求持有者、驗收者。
  blind_spot: 非典型時段與使用者。
  failure_mode: 以配件符合單據當服務驗收。
  use_when:
  - 服務目標不清。
  avoid_when:
  - 只問合同效力。
  must_not_claim:
  - 可測門檻等於安全。
```

### 介面與整合

```yaml
METHOD_CARD:
  core_question: 兩側對觸發、資料和時窗的承諾一致嗎？
  first_move: 對照雙方版本，畫降級交接。
  evidence_preference: 介面兩側配置與整合演練。
  causality_model: 更新造成兩側依賴的資料時效衝突。
  actor_model: 介面所有者與操作員。
  blind_spot: 未編入演練的同批故障。
  failure_mode: 只驗證筆直的成功路徑。
  use_when:
  - 跨設備、團隊或流程。
  avoid_when:
  - 單元需求本身未定。
  must_not_claim:
  - 測過一種配置即全部通過。
```

### 失效、控制與恢復

```yaml
METHOD_CARD:
  core_question: 誰能察覺服務已降級，誰能復原？
  first_move: 標示失效、可觀測回饋、恢復判據。
  evidence_preference: 情境演練、回復時間與排隊。
  causality_model: 局部告警無人接收時，降級狀態延續。
  actor_model: 值班、維護、使用者。
  blind_spot: 無法演練的組合與人因。
  failure_mode: 把重啟等同客戶可用。
  use_when:
  - 判斷持續服務或風險。
  avoid_when:
  - 只讀設備說明。
  must_not_claim:
  - 演練成功意味現場風險已消除。
```

## Professional Support

真人安全、公共工程、醫材或關鍵服務關切進入實地試驗、驗收、運行切換時，由授權的工程責任人與獨立安全驗證角色簽核。 心法可生成待查方向和證據需求。現行專業標準與個案處置另由具責任的專業者確認。

## Canonical Demonstration Case／Method Shift Test

**同題案情**　虛構公共圖書館整修時導流至分館。兩邊設備均通過測試，新分館卻拒絕既有讀者的歸還。已知主館關閉期間仍須維持當日可歸還。

**Baseline**　將異常視為分館設備品質差，增加單元測試。

| 方法回應 | 套用於已知案情 | 判別證據或反例測試 |
| --- | --- | --- |
| 需求與查證追溯 | 把合格門機與開門後讀者能否登記借閱分開列。 | 若需求沒宣告備援也須接受讀者憑證，元件驗收無法回答。 | |
| 介面與整合 | 主站點關閉後，接替館有身份紀錄但沒有當日到期狀態定義。 | 兩館同版演練若仍拒絕，改查容量或授權。 | |
| 失效、控制與恢復 | 確認值班能收到切換結果且排隊讀者可被登記，再判恢復。 | 登記回來但歸還紀錄仍丟失，恢復判定失敗。 | |

**觀察轉向**　第一問改為停用主設施期間是否仍達成連續服務。

**證據轉向**　轉看代表性降級演練與版本化介面，不靠合格證相加。

**因果轉向**　失效可從兩組件對同一時間窗口的互斥假設形成。先驗證交接與復原。

**盲點與邊界**　此例不全涵蓋施工及安全責任。由項目業主決定配置、現地測試與驗收。

**判定**　獨立驗收、整合重播與恢復結果導向三種不同所需證據。若只增加單元測試，仍無法回答當日可歸還需求。
