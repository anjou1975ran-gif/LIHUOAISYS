## 01｜這件事
要保存的不是「上一場參謀本部最後認可什麼答案」，而是**下一個工作節點面對不同問題時，哪些最小關係、生成規則和權限邊界能使它重新形成自己的問題、反對與可追溯判斷。**

已有上位法位明確：`SUMMARY != SEED`、`SEED != SNAPSHOT`、`TARGET-RELATIVE MINIMALITY`、`REGENERATION != REPLAY`。因此不能把本次議事的新詞彙冒稱新發現的 OS 本體。

## 03｜有哪些路？
**候選一：生成規則的最小核心。** 保存指定目標、身份不變量、生成依賴、可變範圍、拒絕條件；新節點用自己的材料形成答案，不必吃進歷史逐字對話。

**候選二：可查的歷史證據解參照。** Archive 保留當時事件、後來審計與未知的法位；SEED 必要時依版本/來源調閱，不能讓後見之明回寫前知。這是一個可與核心分離的來源層，不是把 Archive 全部塞進 Seed。

**候選三：反證／刪減測試契約。** 將 `failure_if_removed` 變成可在陌生題、不同模型條件下被挑戰的主張；不能只因作者寫上「移除必失敗」就叫 minimal。

**候選四：先生成、後回饋的能力遷移。** 不在新節點第一次觀察前預載歷史失敗故事或舊提案。先看它怎麼形成自己的問題，之後才從有法位的史料取得有限回饋。

四者可以共存，也可能因不同再生目標而需要不同組合；**沒有勝者**。

## 04｜最大反對
1. **高度結構化的 SEED 也可能是答題提示。** 讓模型照著寫出六席、多輪反對，仍不證明它在新問題中真的判斷。
2. **歷史案例既可能是必要經驗，也可能是污染來源。** 全面刪除例子可能過於抽象；全部預載可能框死下一個工作節點。
3. **最小性沒有實驗證明。** 沒有進行刪減、陌生題、N0 控制與獨立評審，不能封版。
4. **資料保存不等於可信因果。** Git 的 Event 可證明記錄與序列，不會自動證明跨模型獨立性、內部心理因果或真實能力增益。
5. **成本可能壓過美學。** 極短 Seed 的錯誤與補救成本可能更大；全 Archive 的取回/污染成本也可能更大。

## 05｜還不知道甚麼？
- 哪些關係在陌生題上真的不可移除，哪些只是現行 Staff-HQ 程序的習慣？
- 人類授權、歷史完整性與 Method 先行如何在不同目標下保持身份，而不凍結新框架？
- SEED 要存多少來源 pointer，來源失效時怎樣降級或 HOLD？
- 不同提供者/新模型、不同問題下是否會自然形成合理反對與合法 QUIET？
- 評估怎樣避免把「反對越多越好」當作成功；成本應如何計量？
