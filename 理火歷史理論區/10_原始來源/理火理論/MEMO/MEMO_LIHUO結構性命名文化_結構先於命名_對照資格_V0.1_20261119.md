# MEMO｜LIHUO 結構性命名文化 V0.1
## 結構先於命名 × 對照資格 × 名稱作為結構索引

**日期：** 2026-11-19  
**文件法位：** CULTURE / METHODOLOGY CANDIDATE MEMO  
**狀態：** WORKING / NON-NORMATIVE / NOT RATIFIED / NOT OS PATCH  
**用途：** 記錄理火在長期理論、Runtime、商業化與跨域工作中，對「何時一個新名稱有資格被創造、保留與升格」的文化候選；未來可視實跑結果考慮吸收進 LIHUO OS。

---

# 0｜起點

理火長期工作中，經常出現一個自然傾向：

> 看見新結構 → 立即命名 → 後續理解深化 → 再次改名。

這不是純粹的壞習慣。

因為命名本身具有壓縮、索引、溝通與結構保存的價值。

真正的問題不是：

> **不要命名。**

而是：

> **名字不能先於結構。**

---

# 1｜核心文化句

> **先有對照，才有命名。**

以及：

> **名字是結構的索引，不是結構本身。**

命名的工作，不是替一個直覺貼上漂亮標籤。

命名應該是：

> **對已經存在、可辨認、可比較、可重複使用的結構差異進行壓縮。**

---

# 2｜什麼叫「結構性命名」

一個新名稱至少應回答：

~~~text
1. 它和什麼不是同一件事？

2. 差異發生在哪一條軸上？

3. 邊界如何判斷？

4. 換一個案例後，這個差異是否仍然成立？

5. 這個名稱能否協助分類、診斷、預測、治理或溝通？
~~~

如果這五個問題大部分都無法回答，那個名字目前更接近：

~~~text
RHETORICAL LABEL
TEMPORARY METAPHOR
PERSONAL SHORTHAND
~~~

而不是正式結構概念。

---

# 3｜單獨命名為什麼容易出問題

單獨命名的常見流程：

~~~text
NEW IMPRESSION
↓
NEW NAME
↓
NAME GAINS SALIENCE
↓
LATER EXPLANATION IS FORCED TO FIT NAME
~~~

此時名稱可能反過來污染理解。

也就是：

> **本來只是為了描述結構，最後卻變成結構被迫服務於名稱。**

這會造成：

- 名詞膨脹；
- 概念重疊；
- 同義重命名；
- 後續版本頻繁改名；
- 文件難以維護；
- 新人學到的是名詞，而不是差異；
- 漂亮語言被誤認為理論進展。

---

# 4｜有資格命名的最小形式

候選名稱最好至少存在一組明確對照：

~~~text
A
vs
B
~~~

並且能指出：

~~~text
SAME DOMAIN
+
DIFFERENT STRUCTURAL POSITION
~~~

例如：

~~~text
AI-MADE PRODUCT
vs
AI-NATIVE PRODUCT
~~~

真正的結構差異不是名稱，而是：

~~~text
AI ONLY PARTICIPATES IN DEVELOPMENT
vs
AI PARTICIPATES IN RUNTIME
~~~

名稱只是把這個差異壓縮。

---

# 5｜理火既有例子

## 5.1 Constraint / Direction / PATH

這組名稱有資格保留，不是因為詞彙漂亮，而是它們回答不同問題：

~~~text
CONSTRAINT
→ WHAT SHAPES THE FEASIBLE SPACE?

DIRECTION
→ WHERE DOES FORMATION TEND TO MOVE WITHIN THAT SPACE?

PATH
→ WHAT TRAJECTORY IS ACTUALLY FORMED?
~~~

因此：

~~~text
Constraint != Direction
Direction != PATH
Constraint != PATH
~~~

名稱後面存在結構對照。

---

## 5.2 External Audit / In-Generation Audit

有意義的差異不在「外部／內部」字面，而在：

~~~text
AUDIT AFTER / AROUND GENERATED ACTION
vs
AUDIT PARTICIPATES BEFORE CLOSURE
~~~

若無法穩定區分審計發生的位置與作用階段，名稱本身就沒有足夠資格。

---

## 5.3 AI-Made / AI-Native

真正的差異軸：

~~~text
AI AS DEVELOPMENT TOOL
vs
AI AS RUNTIME COMPUTATION PARTICIPANT
~~~

這是可跨案例重複使用的分類，因此比單一產品名稱更有保存價值。

---

# 6｜暫名與正式名必須分開

不是所有新結構都要等完全證成才可以有名字。

但應分法位：

~~~text
TEMPORARY NAME
=
WORKING HANDLE

FORMAL NAME
=
STRUCTURALLY QUALIFIED TERM
~~~

暫名可以快速溝通。

但暫名不得因為被反覆使用，就自動取得正式概念法位。

---

# 7｜單一案例原則

> **單一案例可以產生暫名，但不足以單獨證成正式結構名稱。**

正式名稱最好至少能：

- 跨兩個以上案例保持同一差異；
- 經過反例後仍保持可辨識性；
- 不與既有概念高度重疊；
- 在實際分類、診斷或治理中產生額外價值。

因此：

~~~text
ONE CASE
→ MAY NAME TEMPORARILY

CROSS-CASE STRUCTURAL DIFFERENCE
→ MAY QUALIFY FOR FORMAL NAMING
~~~

---

# 8｜命名前的遮名測試

候選文化測試：

> **把名字遮掉之後，還剩下什麼可比較的結構？**

如果遮掉名字後，只剩：

- 氣勢；
- 比喻；
- 修辭；
- 情緒；
- 一個特殊案例；

那麼目前沒有正式命名必要。

如果遮掉名字後，仍能看到：

- 差異軸；
- 邊界；
- 對照；
- 失效條件；
- 跨案例重現；

那個名稱才開始具有保存價值。

---

# 9｜命名的合法工作順序

候選工作順序：

~~~text
OBSERVE
↓
DESCRIBE IN PLAIN LANGUAGE
↓
COMPARE
↓
FIND STRUCTURAL DIFFERENCE
↓
TEST ACROSS CASES
↓
CHECK EXISTING TERMS
↓
TEMPORARY NAME
↓
RETEST
↓
FORMAL NAME
~~~

不是：

~~~text
OBSERVE
↓
NAME
↓
BUILD THEORY AROUND NAME
~~~

---

# 10｜命名不是禁止創造

此文化不是「反新名詞」。

理火本身就需要建立新的結構語言。

真正要避免的是：

> **名稱生成速度高於結構生成速度。**

好的命名可以：

- 壓縮複雜差異；
- 保存研究成果；
- 建立跨文件索引；
- 協助人類與 AI 共用概念；
- 提高 Runtime 調用效率；
- 形成可比較的失效分類。

因此正確方向不是減少命名，而是提高命名資格。

---

# 11｜文化候選

候選文化可壓成四句：

> **先描述，再命名。**

> **先對照，再升格。**

> **單例可暫名，跨例才有資格正式命名。**

> **名字是結構索引，不得反過來支配結構。**

---

# 12｜未來進入 LIHUO OS 的可能位置

目前不直接寫入 OS。

若未來實跑證明此文化能穩定降低：

- 名詞膨脹；
- 概念重複；
- 理論漂移；
- 文件版本混亂；
- 模型因名稱產生的假理解；
- 過早封裝；

可考慮放入：

~~~text
LIHUO OS
→ RESEARCH / THEORY CULTURE
→ NAMING QUALIFICATION
→ TERMINOLOGY GOVERNANCE
~~~

但是否進入 OS，仍需另外決定法位與執行方式。

---

# 13｜停止點

本 MEMO 目前只建立文化候選。

不建立新的強制 Gate。

不建立新的獨立模組。

不替這套文化再創造額外專有名詞。

核心只保留：

> **命名不是發明結構；命名是對已成立結構差異的壓縮。**
