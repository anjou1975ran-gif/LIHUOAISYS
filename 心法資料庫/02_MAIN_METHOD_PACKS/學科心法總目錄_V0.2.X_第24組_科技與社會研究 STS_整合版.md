```yaml

  core_question: 每群人怎麼定義技術問題？

  evidence_preference: 原需求、設計決定、使用測試
  causality_model: 哪一問題被框定會改變何者被當錯誤
  actor_model: 窗口、居民、承商

  must_not_claim:
  - 問題沒有物質約束
```

## Professional Support

實際 AI 治理、敏感資料及公共服務門檻需交有授權的治理、工程、法律與受影響者代表審查。 心法可生成待查方向和證據需求。現行專業標準與個案處置另由具責任的專業者確認。

## Canonical Demonstration Case／Method Shift Test

**同題案情**　虛構兩個服務站同用一版登記軟體。一站把待覆核看作該聯繫，另一站先暫停而略去報表。為何看似同系統卻成效不同？

**Baseline**　認定軟體的準確率一定出了問題。

| 方法回應 | 套用於已知案情 | 判別證據或反例測試 |
| --- | --- | --- |
| 社會建構取向 | 兩站把「待覆核」分別當聯繫與暫停 | 若操作紀錄同樣，詮釋假說下降 | |
| 分類及基礎設施 | 暫停站後續報表只見通過者 | 若報表保留全部流程，回饋偏差需重估 | |
| 共同生產與問責 | 查兩站是否同有更正與期限 | 若救濟流程一樣卻結果不同，再查資料與介面 | |

**觀察轉向**　由技術準確率改問何謂「待覆核」及誰有定義權

**證據轉向**　加入規格形成、受影響者經驗及例外決定

**因果轉向**　標記改變後續服務和可見母體，可形成再生的分類偏差

**盲點與邊界**　需取得版本化處理與申訴資料，保留實測問題。

**判定**　三路徑可區分定義、資料回饋與權責。程式責任和法律後果仍需另查。
