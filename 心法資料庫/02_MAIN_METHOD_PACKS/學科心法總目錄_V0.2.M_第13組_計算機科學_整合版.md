## 主要方法取向與心法卡

### 抽象資料與不變量

```yaml
METHOD_CARD:
  core_question: 計算對象是什麼，什麼永遠應成立？
  first_move: 畫狀態及前後條件。
  evidence_preference: 規格、資料定義、狀態快照。
  causality_model: 表示方式引入可區分或被混同的狀態。
  actor_model: 具有狀態的端點和操作發起者。
  blind_spot: 遺漏現實的人或例外。
  failure_mode: 用傳送次數充當預約數。
  use_when:
  - 任務被重複或有狀態歧義。
  avoid_when:
  - 只求政策效力。
  must_not_claim:
  - 資料格式即契約。
```

### 併發操作的正確性

```yaml
METHOD_CARD:
  core_question: 兩個窗口並發時，歷史還能符合承諾嗎？
  first_move: 對照查詢、提交與可見時點。
  evidence_preference: 呼叫和回應先後、提交證據。

  actor_model: 窗口、背景工作與記錄端。
  blind_spot: 外部時鐘不能唯一排序。

  use_when:
  - 有並行接收與競用。
  avoid_when:
  - 可證為純手工登錄。
  must_not_claim:
  - 選定正確性條件等於生產系統已滿足。
```

### 端到端交付與資源界線

```yaml
METHOD_CARD:

```

## Professional Support

涉上線支付、敏感資料或關鍵基礎服務時，由負責的軟體與資安專業在授權範圍核對設計、測試與證據。個案鑑識和部署由責任人確認。 心法可生成待查方向和證據需求。現行專業標準與個案處置另由具責任的專業者確認。

## Canonical Demonstration Case／Method Shift Test

**同題案情**　虛構圖書系統最後一本書同時從兩窗口收到預約。一端逾時重送，兩個畫面聲稱成功，底端提交資料未知。可否把失誤歸為系統太慢？

**Baseline**　將回應視為預約，優先延長逾時。

| 方法回應 | 套用於已知案情 | 判別證據或反例測試 |
| --- | --- | --- |
| 抽象資料與不變量 | 把每次傳送和同一預約意圖分開，檢查每人每書是否只成立一次。 | 如果兩筆已提交且都指向同一意圖，規格反例成立。 | |
| 併發操作的正確性 | 兩窗口都讀到書可預約後各回覆成功。讀要約束後續狀態，才可維持一人成功。 | 若兩讀之後只有一次權威提交且另一窗口更正，和兩筆實際成立的案情不同。 | |
| 端到端交付與資源界線 | 先區分逾時前已提交和一直沒提交，分別核對重試與隊列。 | 若端點收據已完整且重複只在畫面，先改查顯示層，不重判預約成立。 | |

**觀察轉向**　先把閱覽畫面的按鈕成功拆成客端意圖、服務處理與權威狀態。

**證據轉向**　改找同一邏輯意圖的請求和提交紀錄，拿窗內並發事件對照。

**因果轉向**　兩次技術傳送可能仍屬一次預約。狀態定義與提交點決定重複結果，提速未必修復。

**盲點與邊界**　只有畫面不能判定重複入帳。需區分同意圖、兩不同意圖、顯示落差。現場修改需所有者驗證。

**判定**　三方法分別找到表示、交錯、端點交付的可驗證分歧。若能證明只有一次提交，重複預約假說被推翻，但顯示錯誤仍待查。

## Negative Control

**案情**　一張已核版的紙本通知要求讀出發出日期。

**NO_METHOD_WITH_REASON**　對照署名及日期即可。沒有表示衝突或狀態待辨。

**重新開啟條件**　後續若發現兩版本的權威發布狀態不一，再查版本與狀態。
