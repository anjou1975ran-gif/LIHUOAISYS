## 主要方法取向與心法卡

### 可行性與最佳化

```yaml
METHOD_CARD:
  core_question: 哪些選項先被硬限制排除？
  first_move: 列成本、最低服務門檻再比較
  evidence_preference: 預算核准與每情境的服務數。
  causality_model: 限制縮小可改善集合。
  actor_model: 預算與服務責任方。
  blind_spot: 無法衡量的成本。
  failure_mode: 拿權重補硬限制。
  use_when:
  - 資源受限。
  avoid_when:
  - 無權指定門檻。
  must_not_claim:
  - 解必然可部署。
```

### 多目標取捨

```yaml
METHOD_CARD:
  core_question: 哪段改善須付多少成本？
  first_move: 列非支配點和受益群。
  evidence_preference: 成本、分群結果、權重。
  causality_model: 偏好與結果分配共同改變排序。
  actor_model: 服務對象及責任人。
  blind_spot: 群體間效用不可任意換算。
  failure_mode: 把排序寫成普遍最佳。
  use_when:
  - 有競爭目標。
  avoid_when:
  - 單指標已獲授權。
  must_not_claim:
  - 公平由分數決定。
```

### 穩健決策

```yaml
METHOD_CARD:
  core_question: 在未知機率下，誰的失落最大？
  first_move: 比較同組情境下的後悔。
  evidence_preference: 可行基準、情境範圍。
  causality_model: 偏好高度依賴情境時可比較失誤邊界。
  actor_model: 方案執行與後果承擔者。
  blind_spot: 情境清單以外世界。
  failure_mode: 把假想情境當機率。
  use_when:
  - 有深度不確定。
  avoid_when:
  - 只有確定性選項。
  must_not_claim:
  - 穩健即風險為零。
```

## Canonical Demonstration Case／Method Shift Test

**同題案情**　合成公共服務佈點。A 成本 7，晴天／雨天服務 95／40。B 8，85／70。C 9，99／78。預算 8，機率未知。如何比較？

**Baseline**　依晴天服務數選 C 或 A。

| 方法回應 | 套用於已知案情 | 判別證據或反例測試 |
| --- | --- | --- |
| 可行性與最佳化 | 成本上限 8 先排除 C，A、B 可再比。 | 若暴雨服務下限是 60，A 也不可行。 | |
| 多目標取捨 | A 省 1 且晴天較好，B 暴雨仍覆蓋較多。 | 若只許晴天服務且不影響弱勢，新的偏好可能選 A。 | |
| 穩健決策 | A 最大後悔 30，B 最大後悔 10，基準是該情境可行最佳。 | 若暴雨時 B 實際覆蓋只餘 45，兩案優勢差改變，需重算。 | |

**觀察轉向**　先建可行集合及條件，不先列建物名次。

**證據轉向**　讀經授權的預算與覆蓋下限，逐情境核對各案結果。

**因果轉向**　相同路線改變在暴雨與晴天產生不同覆蓋，排序取決於權重或穩健判準。

**盲點與邊界**　情境值是合成數字，不能自設公平權重或措施底線。

**判定**　可行判斷排除 C，且 A、B 最大後悔依序為 30 與 10。此結果會因雨天容量、約束與取捨改變。

## Negative Control

**案情**　一件提案已確認只有一位依法指定的簽署人。

**NO_METHOD_WITH_REASON**　查來源和授權鏈，無需把法定資格當效用排序。

**重新開啟條件**　若已有多個合法備援且風險不同，再進決策模型。
