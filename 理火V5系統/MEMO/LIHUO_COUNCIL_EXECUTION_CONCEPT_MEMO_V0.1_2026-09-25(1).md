# MEMO｜理火會議 × 理火執行：雙專案概念架構

**版本：** V0.1-WORKING  
**日期：** 2026-09-25  
**階段：** 概念保存；不是正式 DAIL、Agent Runtime 規格或部署指令  
**用途：** 下一次討論時快速恢復本次已形成的設計共識，繼續修正。

## 0｜一句話定位

理火會議負責讓提案經過多種思維的連續對抗，留下共同接受的概念、具名異議、未決問題及工程／成本審計結果；理火執行專案負責把已取得交付資格、且原提案節點同意交付的方案寫成企劃，經返會審查和人類簽字後再生產。

**會議的目的首先是紀錄，不是強迫得出結果，更不是直接執行。** 工程審計不能閉合時，完整保存問題就是合法的總會議成果。

## 1｜上下層關係

上層沿用現有理火文件，不另建一套會議憲法：

- **Protocol V2.6：** 根本治理邊界；反自我封聖、邏輯、責任、誠實。AGENT 不能自稱取得宿主或治理權。
- **Lighter V4.6：** 資格、授權、接線、最終放行；已有 DAIL 互動式企畫模組，可供執行專案的企劃階段使用。
- **Main V4.3：** 結構計算引擎；在實際成立的理火週期中，固定 R1／真 R2，SAC O9 必備，I9 有條件介入。**Main R1/R2 不等於會議第一、第二輪。**
- **理火散記 V3.3：** 歷史、失效案例、理論觀察和反省材料；能提供討論來源，但沒有自行修改 Protocol／Runtime 的權限。

下層是**理火會議專案的 `AGENT.md`**：承載五席的思考任務、會議運作、秘書處與紀錄規則。它先是角色與議事規格，不宣稱已啟動五個獨立 AGENT。文件批准也不等於 Host E6／E7 已部署。

## 2｜兩個專案的職責

### A｜理火會議專案（Council）

接受理火節點的理論、修正案、動議案、架構與研究提案。每次召開一場**總會議**，預先設定七至十輪，暫以八輪為預設。每一輪由秘書處留下獨立紀錄；最終形成一份總會議報告。

會議還負責兩種**返會審查**：執行專案企劃書的概念／要求符合性，以及生產成果對已批准企劃書的實作符合性。返會審查不必每次重開八輪；若牽動根本理論，另由提案節點提出修正案，召開下一次總會議。

### B｜理火執行專案（Execution）

只有兩個工作部分：

1. **企劃：** 接收已獲會議同意交付、且原提案節點明確同意的同一版本方案；利用 Lighter 既有企畫能力，提出具體企劃書。
2. **生產：** 企劃書返會無實質阻斷異議，並獲人類就特定版本、範圍正式簽字後，才開始程式生產、測試及交付。

執行專案不自行裁決原提案理念，也不以工程方便為理由靜默改寫已批准企劃。

## 3｜理火會議五席：目前的合併結果

| 席位 | 思考職責 | 固定提問 |
|---|---|---|
| **A｜可能性擴張**（探索＋觸發＋理念） | 沿著原提案持續尋找尚未出現的 PATH、張力、新概念；不負責過早收斂 | 「在這個提案的基礎上，還能長出什麼？」 |
| **B｜架構轉向**（反傳統架構＋結構聯想） | 分析原提案是否受慣性框架限制；尋找其他領域的相似結構，提出替代路線 | 「為何不走另外一條路？能不能翻桌重來？」 |
| **C｜概念審計** | 檢查定義、前提、證據、因果與責任；提出清楚、可追蹤的異議 | 「這個主張憑什麼成立？」 |
| **D｜工程審計** | 檢查技術路線、依賴、必要工具、實作能力、可測試性與失敗恢復 | 「要把它做出來，條件成熟了嗎？」 |
| **E｜成本審計** | 檢查開發、運行、維護、制度及機會成本，說清估算依據與不確定性 | 「要付出什麼代價？有沒有成本不同的替代路線？」 |

五席不是五種語氣。A、B 都創造可能性，但 A 擴展**原問題空間**，B 可以改寫**問題空間本身**；C 審成立資格，D 審工程條件，E 審資源代價。E 不應在首輪拿成本未知當作壓制創造的理由。C、D、E 的審計結果都應列入最終報告；高成本不等於概念錯誤。

秘書處另設，不是第六位思想席，不參與論點勝負裁決。

## 4｜一次總會議如何運作

- **會前：** 固定原提案版本、提案節點、參考資料、預設輪數和本次討論範圍。
- **第 1 輪：** 五席先獨立提交各自初評，避免先讀其他席的發言造成附和；秘書處輸出 `MR01`。
- **第 2 輪起：** 全員根據上一輪正式紀錄提出新的可能、回應他席、找出對方問題或修正自身主張；每輪輸出一份新紀錄 `MR02`、`MR03`……。
- **前期（約 R1–R3）：** 以探索、觸發、替代架構與擴張為主，不急著淘汰想法。
- **中期（約 R4–R6）：** 以交叉審計、具體反例、證據、工程與成本條件為主。
- **後期（約 R7–R8）：** 整理共同接受的概念、有效異議、未決問題與可交付性；收斂的是**紀錄**，不是強迫 A 停止探索或 B 停止翻桌。

輪數預先確定，會影響各席如何分配探索和驗證；輪數用盡仍不成立的東西，合法留待下一次總會議。後期重大新反例不能因接近結束就被忽略。

## 5｜總會議最終報告要留下什麼

每次總會議都出一份**不可覆寫的獨立報告**，至少包含：

1. 原提案及本次總會議的參考版本。
2. **共同接受的概念：** 明確寫出接受內容、成立條件，以及哪些席位明確接受；沉默不算同意。
3. **具名異議：** 異議編號、由哪個 AGENT 提出、針對什麼、理由、被誰回應、目前仍有效／部分解決／撤回。原始異議與修正歷史不得抹掉。
4. **未決問題：** 尚無足夠依據判斷，也不等於有人反對。
5. **工程與成本審計：** 可行路線、必要條件、缺少的能力、測試要求、成本與預算依據及不確定性。
6. **是否具備交付企劃的資格：** 若工程、成本或其他實質阻斷缺口未閉合，就只能交還提案節點研究，不能送執行專案開案。

會議可以形成多個仍具資格的方案；不強迫只有一個結論。`無異議` 是明確確認的紀錄狀態，不是自動宣稱理論已被證明。

## 6｜會議與執行之間的雙重交付

即使總會議同意交付，最終報告仍須**同時交給原提案節點**。執行專案要開始企劃，必須收到兩份對應同一方案版本的材料：

- **第一份：會議交付同意及要求**——本次總會議已完成必要工程／成本審計，列明合格方案、限制、要求及尚存的非阻斷異議。
- **第二份：原提案節點的知情交付同意**——節點確已取得該次會議結果，明確接受把哪一個版本、哪一個範圍送去企劃。

缺一份就 HOLD。會議同意不能取代提案節點同意；提案節點同意不能取代會議的可行性審計。提案節點不同意討論結果，可以提出修正案或新動議，召開第二次總會議。

**雙重同意只准「開始企劃」，不直接准許生產。**

## 7｜企劃、生產及返會閉環

`會議總報告 + 提案節點交付同意` → 執行專案**企劃組**編製企劃書 → **返會糾錯審查**：

- 若有實質異議：秘書處逐項記錄提出席位及理由，退回企劃組修正新版，再返會。
- 若無實質阻斷異議：固定企劃書版本，送**人類最終簽字**。
- 人類批准指定版本與範圍後，執行專案**生產組**才開始編寫、測試、交付。
- 程式和測試資料完成後，送回會議做**實作符合性審查**。程式錯誤退回生產；核心意圖需要改變，退回企劃，必要時由提案節點再提修正案並重新開總會議。

會議不是 Host Executor。企劃通過、程式通過會議審查、已實際部署，是三件不同的事；不得互相冒充。

## 8｜`AGENT.md` 內部建議怎麼寫（先求清楚，不做大型規格）

目前先**只用一份共用 `AGENT.md`**，不用急著分成五套人格長文件。最小目錄建議：

```text
AGENT.md
  0. 專案身份與邊界
  1. 上層文件：Protocol / Lighter / Main / Miscellany
  2. 五席任務：A / B / C / D / E
  3. 秘書處：記錄、署名、版本、不裁決
  4. 一次總會議：提案 → 7–10 輪 → 每輪紀錄 → 總報告
  5. 總報告：共同概念／具名異議／未決／工程／成本／交付資格
  6. 對外接線：原節點知情同意 + 會議同意 → 執行企劃 → 返會 → 人類簽字 → 生產 → 返會
```

`AGENT.md` 每一席的說明先維持四個欄位：**任務、固定問題、不得做什麼、該交出什麼紀錄**。例如 A 的輸出是新 PATH 而不是選定方案；B 的輸出是替代架構及類比失效條件；C 是具名概念異議；D 是工程依賴與閉合缺口；E 是成本分類、估算依據及資源缺口。

秘書處只做：固定當輪輸入、收集五席發言、編製每輪紀錄、維護異議追蹤、生成總報告、核對交付所需兩份材料。它**不能自己創造共識、消除異議、替提案節點同意，或自行授權生產**。

若日後需要真正的獨立多 AGENT 執行，再討論每席是否拆成獨立檔、共同上下文如何隔離、秘書處如何可靠保存逐輪原始發言，以及 Host 實際調度與證據。現在不預先宣稱已有這些能力。

## 9｜目前保留的開放問題

- 五席是否每場全部出席；若縮編，C／D 不得缺席，涉及交付時 E 的成本審計必須有明確負責者。
- 總會議的七至十輪如何控制討論成本、上下文長度與跨輪記憶失真。
- 企劃返會審查採幾輪、什麼情況才需要重新召開完整總會議。
- 工程與成本的「閉合」如何定義最低證據門檻；哪些屬阻斷，哪些僅需具名保留。
- 五席真正獨立運行、秘書處保存機制、跨專案交接、外部工具證據與 Host E6／E7，皆仍待工程設計及實測。
