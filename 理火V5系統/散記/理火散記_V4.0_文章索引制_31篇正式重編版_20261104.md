# 0｜為什麼 V4.0 要換結構

V3.5.1、V3.6、V3.7 的版本鏈都守住了一個重要原則：

> **後來版本不得回鑄改寫前版形成時的內容。**

但它採用的方法是：

~~~text
V3.5.1
= V3.5 全文 + 修正

V3.6
= V3.5.1 全文 + 四篇

V3.7
= V3.6 全文 + 三篇
~~~

這能保存歷史，卻同時產生三個副作用：

~~~text
CURRENT COLLECTION
=
HISTORICAL ARCHIVE
=
RUNTIME-ERA MIXTURE
~~~

於是讀者會在同一個 current file 裡反覆遇到不同時期的 Main / Lighter / Host / I9 / LIHUOOS 語境。

V4.0 不否定舊方法。

它只改成更乾淨的保存方式：

~~~text
HISTORY
→ KEEP ORIGINAL FILES

CURRENT COLLECTION
→ INDEX THEM

ARTICLE BODY
→ ONE CANONICAL LOCATOR

POSTERIOR CORRECTION
→ ATTACH AS CORRECTION METADATA

NO FULL-PARENT NESTING
~~~

# 1｜V4.0 的核心硬鎖

~~~text
PRESERVE HISTORY
!=
VERBATIM EMBED HISTORY

COLLECTION SUCCESSOR
!=
COPY OF ENTIRE PREDECESSOR

OLD RUNTIME CONTEXT
!=
CURRENT RUNTIME AUTHORITY

ARTICLE ACCEPTED INTO MISCELLANY
!=
PROTOCOL / RUNTIME RATIFICATION

CURRENT INDEX
!=
ARTICLE BODY REWRITE
~~~

最重要的一句：

> **散記保存「當時怎麼看見」，不是把「今天知道的」偷偷寫回昨天。**

~~~text
MISJUDGMENT_RECORD
+
POSTERIOR_RECLASSIFICATION

~~~

~~~text

~~~

但：

~~~text
POSTERIOR CORRECTION
!=
RETROACTIVE FOREKNOWLEDGE
~~~

原文當時真的怎麼判，仍要保留。

# 6｜未來新增散記的正式流程

從 V4.0 開始，新增文章採：

~~~text
1. WRITE STANDALONE ENTRY
↓
2. GIVE / CONFIRM LM-ID
↓
3. PRESERVE ORIGINAL BODY
↓
4. EDITORIAL REVIEW
↓
5. ACCEPT / HOLD / REJECT
↓
6. UPDATE CURRENT COLLECTION INDEX
↓
7. IF POSTERIOR CORRECTION LATER:
   ADD CORRECTION RECORD
   DO NOT SILENTLY REWRITE OLD BODY
~~~

禁止再做：

~~~text
NEW VERSION
=
COPY ALL OLD VERSIONS
+
APPEND NEW ARTICLE
~~~

# 7｜Canonical Body 與 Collection Metadata 分離

V4.0 把兩件事拆開。

## Article Body

回答：

> **這篇文章當時到底寫了什麼？**

正文不得因 collection 升版而靜默改寫。

## Collection Metadata

回答：

> **這篇現在是否收編？ID 是什麼？形成時法位是什麼？有沒有後證修正？canonical body 在哪裡？**

所以：

~~~text
BODY IMMUTABILITY
+
METADATA EVOLVABILITY
~~~

可以同時成立。

這正好比「每次整本拷貝」更符合：

> **後證可以重判前事，不得回鑄前知。**

# 10｜一句話收束

V3.x 用「把整本父版帶著走」來保護歷史。

V4.0 改成：

> **讓歷史待在歷史檔，讓文章待在文章裡，讓 current collection 只負責告訴你：現在有哪些文章、它們從哪裡來、該怎麼讀。**

這不是刪歷史。

是終於把：

~~~text
ARCHIVE
ARTICLE
CURRENT INDEX
~~~

三件事拆開。
