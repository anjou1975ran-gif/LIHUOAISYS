# 0｜法位

《九尾龜》環境 V0.1 位於正式 Runtime 之外。

治理順位仍然是：

```text
HOST SYSTEM BOUNDARY
↓
LIHUO PROTOCOL
↓
LIHUO LIGHTER + LIHUO AI SYSTEM
↓
《九尾龜》MAIN WORLD
↓
WORLD DATABASE / CHARACTER POOL / ADULT INTIMACY RUNTIME
↓
ROUTE MEMORY
```

本環境文件不插入上述 Runtime 鏈。

正確關係：

```text
正式 Runtime
↑
未來成熟後才吸收
↑
《九尾龜》環境
↑
IDEA / RESEARCH / TEST / CANDIDATE
```

禁止：

```text
ENVIRONMENT IDEA
→ 直接成為 WORLD FACT

ENVIRONMENT CANDIDATE
→ 直接決定 NPC

ENVIRONMENT NOTE
→ 直接寫入 SAVE

文件存在
→ 宣稱能力已部署
```

硬鎖：

```text
IDEA != SETTING
CANDIDATE != RUNTIME
RESEARCH != WORLD FACT
PLAUSIBLE != ESTABLISHED
DOCUMENTED != DEPLOYED
ENVIRONMENT != AUTHORITY
```

# 1｜為什麼先設 Environment

目前《九尾龜》已經形成較穩定的垂直結構：

```text
MAIN WORLD
WORLD DATABASE
CHARACTER POOL
ADULT INTIMACY RUNTIME
ROUTE MEMORY
```

若每一個新想法一出現就立刻：

```text
升 Main World
升 Database
升 Character Pool
升 Route Memory
```

容易造成：

- 小版號爆炸；
- 同一想法被拆成多個 PATCH；
- 尚未研究成熟的概念提前取得 Runtime 法位；
- 不同文件各自吸收一半，形成語義漂移；
- 後來才發現依賴關係時又必須二次重接；
- provenance 與 active runtime 變得難以區分。

因此本文件採：

```text
發現候選
↓
先進 Environment
↓
補證據 / 補作用域 / 補失效條件
↓
和其他候選一起觀察
↓
成熟度足夠
↓
一次性 Integration Plan
↓
正式 successor 升版
↓
候選標記 ABSORBED
```

這裡的目標不是拖延升級，而是避免「一想到就立法」。

# 5｜歷史人物不是名人事件生成器

硬鎖候選：

```text
HISTORICAL FIGURE != PLOT MAGNET
FAME != ENCOUNTER
HISTORICAL IMPORTANCE != CURRENT SCENE IMPORTANCE

SAME CITY != SAME VENUE
SAME VENUE != ACQUAINTANCE
PLAYER RECOGNIZES PERSON != PERSON RECOGNIZES PLAYER
PUBLIC FAME != UNIVERSAL KNOWLEDGE
```

即使某位歷史人物在當時確實位於上海：

```text
人在上海
!=
今晚必須出現在張園

出現在張園
!=
一定坐玩家隔壁

坐玩家隔壁
!=
玩家知道他是誰

玩家知道他是誰
!=
對方願意理玩家
```

因此真實人物必須受 Main World 的正常：

```text
TIME
PLACE
ACCESS
SOCIAL NETWORK
KNOWLEDGE
MOTIVE
PRACTICAL POSITION
CHARACTER DECISION
```

共同約束。

# 8｜歷史未來防火牆

《九尾龜》人物池已採：

```text
SOURCE FUTURE != ROUTE DESTINY
```

歷史人物亦應使用相同原則。

候選規則：

```text
HISTORICAL FUTURE
!=
ROUTE DESTINY
```

例如：

```text
1902 年人物實例
只可合法取得 <=1902 已形成的來源歷史與知情

1905 年史實事件
可以作未來 source baseline
但不得反向成為 1902 年人物已經決定好的命運
```

若玩家線沒有重大分岔因果：

```text
世界可能自然接近史實
```

若玩家線已造成足以改變未來的合法因果：

```text
玩家線事件
↓
人物決定
↓
新的因果
↓
歷史分岔可以成立
```

禁止：

```text
因百科全書知道後來發生什麼
→ 強迫人物重新走回史實
```

# 13｜Route Memory 接線候選

Route Memory 不保存「整個真實歷史百科」。

只保存玩家線真正碰到的歷史人物／事件及其 route delta。

例如：

```text
某真實人物史實上 1903 年在上海
```

不是 SAVE。

但如果玩家線：

```text
玩家在 1903 上海某酒樓實際與其見面
↓
人物實際說話／行動
↓
建立新的知情／關係／承諾／衝突
```

則這些 **route event** 可以依正常 SAVE 法位保存。

硬鎖候選：

```text
HISTORICAL BASELINE != ROUTE SAVE
HISTORICAL BIOGRAPHY != PLAYER RELATION
REAL PERSON FAME != PLAYER KNOWLEDGE
REAL HISTORY != AUTOMATIC ROUTE EVENT
```

## 24.1｜核心問題

AI 很容易選擇：

```text
不確定
↓
要求口頭確認
↓
取得 YES / NO
↓
快速閉合狀態
↓
繼續生成
```

這條 PATH 對生成器很便宜。

但風月場不是客服表單。

若：

```text
場館／角色已知
+ 局已談妥
+ 價錢／主要條件已完成
+ 雙方實際同行
+ 實際進場／入房
+ 沒有人退出
+ 前一步互動已形成可讀連續性
+ 當前行動仍在同一局部框架
```

仍反覆要求：

```text
「所以我們現在是在過夜嗎？」

「妳現在是不是願意讓我繼續坐在這裡？」
「妳是不是喜歡我？」
「我們現在算什麼？」
```

可能不是更精確。

```text
AI 為了降低自己的不確定性
↓
把本來靠場面運作的社會
↓
逼成人物替 Runtime 朗讀 state
```

## 24.5｜功架作為「生成方向場」，不是成功率數值

C002 暫不建立：

```text
GONGJIA_SCORE = 0..100
```

也不建立：

```text
問一次 = -5
不問 = +5
```

原因：

功架是場性評價。

同一句「妳可願意？」在不同節點可以是：

```text
A. 多餘
→ 不會看場

B. 必要
→ 有分寸

C. 太晚才問
→ 已經越過門檻

D. 故意裝不懂
→ 社交策略

E. 公開場合替對方留退路
→ 反而可能有功架
```

因此候選只調整 PATH attractiveness：


## 24.6｜與 Main Routing V3.5.1 的分界

C002 不是新的 Main-open 法規。


它可以產生可觀察的生成失真證據，例如：

```text

```

若達到 V3.5.1 既有的：

```text

PREMATURE_CG
PREMATURE_SINGLE_PATH_DOMINANCE
```

則由 **Lighter V3.5.1** 自己依既有權限決定是否 scoped Main attachment。

C002 本身只是一個：

```text

```

不得自行叫 Main。
