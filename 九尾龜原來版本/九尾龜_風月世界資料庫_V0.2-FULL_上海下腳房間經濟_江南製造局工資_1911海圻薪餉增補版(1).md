# 0｜資料庫法位與使用方式

本資料庫不是 FMS 2.0，也不是另一套 Main System。

它不做：

```text
NPC 決策
世界事件 commit
玩家成功判定
關係升級
同意判定
SAVE
```

它只提供：

```text
SOURCE-GROUNDED WORLD KNOWLEDGE
+ CITY/TIME/VENUE SCOPE
+ TERM SEMANTICS
+ PRICE/CREDIT EVIDENCE
+ ROLE/VENUE FUNCTIONS
+ KNOWN COUNTEREXAMPLES
+ SOURCE_CONFLICT
+ UNKNOWN
```

主世界可依當前場景查本資料庫，再讓 LLM 形成世界／人物反應。

最短式：

```text
MAIN WORLD
asks:
  "現在蘇州書場有哪些制度可用？"

DATABASE
returns:
  "公開展示／點戲／堂倌介紹／大姐初次接觸／可導往住所；
   書場 != 私人房間；
   CH1 source anchor."

MAIN WORLD
then decides:
  who is present
  who says what
  who accepts / refuses
  what actually happens
```

# 2｜資料庫總硬鎖

以下不是 Runtime 決策規則，而是資料語義的防混淆鎖。

```text
MONEY != RELATION
PAYMENT != ACCESS
ACCESS != RELATION
RELATION != CONSENT

CALL REQUEST != OUTCALL
OUTCALL != ARRIVAL
BANQUET != PENGHE
PENGHE != OVERNIGHT
OVERNIGHT != RELATION QUALIFICATION

ACCOUNT != CASH
RECEIVABLE != COLLECTED CASH
FACE RECEIVABLE != EXPECTED COLLECTION != ACTUAL COLLECTION
SERVICE PRICE != GRATUITY != TABLE FEE != SEAT FEE != GIFT != SUPPORT PAYMENT
DEBT != OWNERSHIP

PUBLIC LABEL != PRIVATE RELATION FACT
RUMOR != FACT
MEDIA SIGNAL != WORLD TRUTH
PUBLIC RANK != QUALITY
CLIENT FLOW != REPUTATION
REPUTATION != CHARACTER TRAIT

CITY RULE != GLOBAL RULE
CITY LEXICON != SPEAKER DIALECT
VENUE REGISTER != PERSONALITY
ROLE != IDENTITY

BUSINESS EXIT != MARRIAGE
MARRIAGE INTENT != COMPLETION
COHABITATION != MARRIAGE
DEATH != HISTORY RESET

PORTABLE HISTORY != PORTABLE LOCAL STATUS
```

任何條目若與上述分軸衝突，優先退回來源重新判讀。

# 4｜CITY PROFILE｜城市不是皮膚

## DB-CITY-SUZHOU｜蘇州

```yaml
CITY_PROFILE:
  id: "DB-CITY-SUZHOU"
  city: "蘇州"
  core_features:
    - "書場可作風月市場公開發現入口。"
    - "書場、書寓／堂子、倌人住所、酒席、虎丘／山塘／遊船可形成多節點社交鏈。"
    - "酒席存在每客檯面洋錢。"
    - "叫來倌人可形成坐場洋錢。"
    - "局帳與坐場現金曝險分離。"
    - "碰和制度存在形成史。"
    - "受邀赴酒仍可能需要被邀客自行支付檯面等成本。"
  household_model:
    primary: "ROOM/HOUSEHOLD + SHUCHANG DISCOVERY"
  source_anchors: [1,54,52,60]
```

蘇州的重要結構不是「上海堂子換地名」，而是：

```text
SHUCHANG DISCOVERY
→ PUBLIC PERFORMANCE
→ INITIAL SOCIAL CONTACT
→ ROUTING / INVITATION
→ RESIDENCE / BANQUET / OTHER NODE
```

CH1 可確認初到蘇州者先住佛照樓，再到餘香閣書場；書場本身是公開演唱、看人、點戲與認路入口，不等於倌人私人房間。

只證明 composite account 有多種 transaction family；不能反解每項單價。

# 30｜SHANGHAI 下腳語義校正

## 30.1 下腳的第一層受款語義

```yaml
SHANGHAI_XIAJIAO_SEMANTIC:
  term: "下腳"
  primary_external_definition:
    - "妓家場域中犒賞男女傭僕／房間服務人員的款項。"
  economic_function:
    - "房間／妓院 household economy 的周邊人員收入來源之一。"
    - "可包含服務、車轎／轎飯、節慶、住夜等場景的分配與犒賞意味。"
  NOT_EQUAL:
    - "倌人本人公開夜價"
    - "固定性交費"
    - "所有上海妓院統一 tariff"
    - "純粹自願小費"
```

> **RUNTIME HARD LOCK：不得讓倌人以「我的下腳就是我的身價／我的夜價」作為通用制度性報價。**

《九尾龜》正文中的 20 / 20 / 50 / 40 等下腳案例仍保留，但 V0.2 改變其解讀方式：

```text
大額下腳
may indicate
FACE / STATUS / GENEROSITY / ROOM-HOUSEHOLD DISTRIBUTION

but does NOT automatically mean
COURTESAN PERSONAL NET INCOME
or
SEX PRICE
```

## 30.2 長三：不公開「夜合之資」

《清稗類鈔》記長三：

```text
留宿
→ 不公開言夜合之資
→ 簿上不直接記夜合費，只作隱約標識
→ 須有下腳，至少銀幣十圓
```

因此在長三 scope 內：

```yaml
LONGSAN_OVERNIGHT:
  explicit_sex_tariff: "NOT THE NORMAL PUBLIC ACCOUNTING FORM"
  overnight_event: true
  xiajiao_required_or_expected_in_source: true
  source_minimum_example: 10
  currency: "銀幣圓"
  caution:
    - "十圓是外部史料中的場域／時期例，不是《九尾龜》全上海固定價。"
    - "留宿 != 性交必然發生。"
```

這也修正 V0.1／先前 STORY 中容易產生的錯誤抽象：

```text
上海長三住夜
!=
固定『夜合費』 + 額外下腳
```

目前更安全的 Runtime 表達是：

```text
OVERNIGHT EVENT
+
ROOM/HOUSEHOLD ACCOUNTING
+
XIAJIAO / OTHER SCOPED OUTLAYS
+
PRIVATE / TACIT ARRANGEMENT
```

不可為了帳目漂亮而自行補一筆不存在的 universal `SEX_FEE`。

# 31｜么二「六跌倒」：最小留宿交易骨架

《清稗類鈔》記光、宣間么二有「六跌倒」之說：

```yaml
YAOER_SIX_YUAN_OVERNIGHT_BUNDLE:
  epoch: "光緒末—宣統前後之歷史語境"
  venue_class: "么二"
  currency: "銀幣圓"
  components:
    移茶: 1
    轉局: 1
    夜廂: 2
    下腳: 2
  total: 6
  explicitly_excluded:
    - "叫局"
    - "吃酒"
    - "碰和"
```

語義：

```text
移茶1 + 轉局1 + 夜廂2 + 下腳2 = 6
```

其中「夜廂」是么二以下留客住宿的制度詞；長三不使用這個詞。

### 31.1 這個 1+1+2+2 的價值

它不是全上海價目表，而是一個非常好的**交易拆帳模板**：

```text
CLIENT TOTAL SPEND
=
ACCESS / SERVICE ITEMS
+
ROOM / HOUSEHOLD ITEMS
+
OPTIONAL SOCIAL DISPLAY ITEMS
```

所以：

```text
客人花 6
!=
姑娘個人拿 6
```

而 `下腳2` 的外部方言證據，更直接指向男女傭僕／房間服務體系。
